# Compatibility contracts

This document is the status ledger for DotReticulum's compatibility with the pinned upstream Reticulum reference. Each row names one upstream contract, cites where it lives in the pinned source, and records how much of it the native implementation covers, what evidence backs that, and where the evidence stops.

DotReticulum is an experimental, AI-assisted, independent implementation. It is not an official or endorsed Reticulum implementation. Here, "compatible" means that a specifically described behavior has a native implementation and evidence at the stated boundary. It does not imply complete API, platform, malformed-input, topology or feature parity.

## The reference

The current live reference is Reticulum (RNS) 1.5.7 at `a29bfb51c468945c96a1ee22cae0114e993e2391`. The LXMF reference is 1.2.1. Older vectors keep their original provenance at `e40191b3d193b46b7f2d8a44424a594cd758839b`.

Source paths and line ranges in the tables refer to the pinned upstream checkout. Test and generator names are repository paths or test class names. Evidence is limited to the behavior those artifacts actually exercise.

## How to read the ledger

Each row describes one contract. The first column names it and cites the pinned source. The second column starts with the **status**, followed by a short description of what is implemented, the evidence letters and test names that support it, and finally its limits and intentional differences.

### Status vocabulary

| Status | Meaning |
| --- | --- |
| **Implemented** | Native code and evidence cover the specifically stated behavior. This is not a claim that every input, platform, topology, or API is equivalent. |
| **Partial** | Some behavior is implemented, while named behavior is missing, deliberately restricted, or not fully accepted. Differences and bounds remain stated. |
| **Not implemented** | The applicable reference behavior has no native equivalent. An explicit rejection is not equivalent behavior. |
| **Unverified** | Available evidence does not establish the specified behavior; this does not assert that code is absent. |
| **Not applicable** | The behavior is absent from the pinned reference, is Python-specific implementation machinery, or is outside the stated scope. Associated wire/process behavior is not excluded. |
| **Upstream placeholder** | The pinned reference declares but does not implement or enable the behavior. Observable parser and rejection behavior can still be in scope. |

Statuses describe individual contracts, not confidence scores. A family can have an implemented valid-input behavior alongside partial failure, platform or topology coverage. Missing implementation, failed acceptance, unavailable hardware and upstream placeholders are different things, and the ledger keeps them apart.

### Evidence letters

- **V** — independently executed upstream vectors. See the named `Generate*.py` script and the fixture's provenance.
- **U** — managed unit, loopback or simulator tests. These are not Python interoperability.
- **L** — an actual pinned Python peer, in the stated roles and topology.
- **P** — separate-process Pester acceptance, including process and filesystem effects.
- **N** — the published native executable ran the feature, not only `--help`.
- **H** — named physical hardware, as distinct from a device simulator.

## How compatibility is tested

Compatibility is tested in two separate ways. The shared **Compatibility** suite runs upstream-advertised claims against both the reference and DotReticulum. Contract **integration** checks, which are .NET-only or mixed-peer, run separately under **Test** and are not promoted into shared Compatibility. Most rows in this ledger cite xUnit and integration evidence; the shared suite is a smaller, stricter layer on top.

### Shared claim scenarios

Each shared scenario is a readable Pester test under `tests\Compatibility\Claims`. The same scenario, inputs and assertions run against the Python reference and against the published native .NET executable on Linux, macOS and Windows. Only the invocation adapter changes between candidates.

Multi-node scenarios keep the actual pinned upstream as the fixed peer. Upstream-to-upstream runs first as the baseline, and then only the candidate is replaced with the native binary. Python used merely as a peer never establishes an Upstream pass.

`tests\Compatibility\Get-CompatibilityTests.ps1` discovers the tests and joins them with their upstream citations without executing anything. Uncovered advertised claims stay visible in that inventory. The shared inventory currently has **42 distinct tests and 17 catalogued claims**, recorded in `tests\Compatibility\catalog.json`. A count of tests is the number of distinct Pester `It` cases, not the number of per-platform executions.

### Retrieving the reference

Each native candidate fetches its own reference. The [Test workflow](../.github/workflows/test.yml)'s Compatibility jobs use the candidate's own `rngit` over `rns://`, reaching the hosted source through two public TCP gateways, `rmap.world:4242` and `node.reticulumnet.nl:4242` (see `tests\Compatibility\Invoke-CompatibilityTests.ps1`).

The local repository is seeded only with history up to the pin's parent from the GitHub comparison mirror, and the seed is recorded with its provenance. The retrieval case then requires that:

- the pinned commit was initially absent,
- the Reticulum bundle carried a nonzero number of bytes,
- `git fsck --full --strict` passes, and
- the pinned commit and tree match exactly.

The fetched development head is recorded separately. An advancing upstream head never silently moves the pin, and object consistency is not publisher authentication.

One verified source bundle, from the Linux candidate, is retained with its SHA-256 and reused by Test and by the subsequent Python baseline. There is no separate fetch workflow.

### Reading the report

The Compatibility summary is a table with one row per real Pester `It`, showing its outcome on Upstream, Linux, macOS and Windows. Rows are not calculated claim verdicts. Each Test ID links to the shared test source at the executing commit.

Source quotations in the catalog are checked against the fetched pin. The catalog's `citation.uri` / `CitationUri` field stays blank unless primary-source navigation has been verified, and there is no GitHub fallback. All 17 current claims have verified HTTPS links to real sections or API definitions in the official published manual, including matching claim text. That website identifies itself as **1.5.5**, not our **1.5.7** pin, so these navigation links do not replace the exact pinned source citations, move the reference or establish compatibility. No guessed NomadNet URLs, source-line anchors, custom URI schemes or GitHub fallbacks are used.

Windows `rncp` peer cases disclose a reference-side file-retention workaround; see [Contributing](../.github/CONTRIBUTING.md#moving-to-a-new-upstream-release).

### What the shared cases do and do not show

The shared cases are bounded evidence, not comprehensive parity. The Channel case covers Buffer message encoding only, not the general reader/writer APIs, loss or soak. The routing cases do not establish alternate routes, RF or impaired meshes. The notable bounded cases are described below.

**Management requests (T053, T054, T058 / C008).** These drive the actual candidate `rnstatus` CLI against the same pinned upstream management endpoint. The small response must fit the observed link MDU. The larger case keeps 24 owned TCP connections open, waits for their actual upstream child registration, then requires a packed response larger than that MDU and exact agreement between all returned interface names and the peer's generated response. Pinned `Link.py:845-854` carries such larger responses as resources; there is no response padding or replacement serialization. The observer delegates to the original status generator with its existing identity allowlist, and **T054** also requires that a denied identity never invokes that generator. All four hosted candidates passed these cases in run **40956389129**. They are bounded management request/response cases, not full Request/Response acceptance.

**Remote execution (T059 / C008).** This drives the actual candidate `rnx` CLI against an allowlisted upstream execution listener. The same fixed command persists and echoes **21,874 bytes** of ASCII-safe input. The test requires exact persisted bytes and returned output, the authenticated identity, the actual request-resource advertisement and ID, and both packed request and response above the observed MDU. The thin observer delegates to the original command generator and uses normal resource callbacks; it does not replace protocol methods, timers or responses. Windows published-native and upstream-to-upstream executions passed locally, then all four hosted candidates passed in run **40961479281** at source **67eaa41**, with all four reports at **42 passed / zero failed**. This does not establish arbitrary application values, multiline console-byte equivalence, concurrent requests, timeouts/cancellation or general remote-execution parity.

**Channel streams (T057 / C009).** This drives the actual candidate `rnsh` CLI against a pinned upstream Channel application that uses the `Buffer.StreamDataMessage` subclass from `rnsh/protocol.py:100-107`. Both directions persist and compare distinct, exact, ordered stream bytes and observe EOF across multiple messages. The application does **not** execute a subprocess: this is Channel/stream-message acceptance, not remote-execution acceptance or a replacement upstream listener. It does not cover the public RawChannelReader/Writer APIs, loss or reordering, sustained soak or arbitrary binary stdout. Both candidates use precreated, owned shell-state directories. This keeps the upstream CLI's ordinary new-directory notice from contaminating its stdout before logging initializes, without filtering output or patching upstream. Local Windows NativeAOT and actual Linux upstream-to-upstream executions passed, followed by all four hosted candidates in run **40915647175** at source **52dc6f0**. Separate impaired-mesh failures in that run neither invalidate nor expand this bounded case.

## Adapters, shims and what they do not prove

`tests\Interop\reference_environment.py` checks that RNS is actually imported from the selected checkout, at the exact SHA, with clean tracked `RNS` sources. When LXMF is used, it checks the distribution's import path and version 1.2.1. Tests must opt in, or explicitly skip with a reason, when the required peer or platform is absent.

Adapters drive the real upstream APIs. Their existence does not make every underlying CLI, UI or backend path an unmodified execution.

| Evidence adapter / setting | Disclosure and claim boundary |
| --- | --- |
| `Interop\rncp_win_shim.py` | On Windows, replaces upstream's move of an open resource with a copy. Wire and resource behavior still use Python, but **unmodified upstream Windows receive/filesystem behavior is not verified**. |
| `Interop\live_rngit_client.py` | On Windows, closes the received resource immediately before the original retention callback moves it. The actual upstream client and handlers are retained. This is not unmodified Windows file-lifetime behavior. |
| Resource vector generators | Frozen randomness, and reversible XOR in place of link encryption. They give exact segmentation, compression, hashmap and state evidence only. Live/native encrypted resources and the retry-crypto vectors independently supply crypto evidence. |
| Channel window vectors versus retry-crypto vectors | A synthetic outlet, clock and receipts prove state. The separate real Packet/Link/Token/Transport retry path uses an installed synthetic session key and capture sink: it proves fresh ciphertext, hash and receipt, but **not the handshake or network**. |
| Auto/Backbone/Pipe/Stream/KISS/RNode/Weave/I2P generators | Controlled clock, socket, serial, thread, epoll, queue and existence adapters, or `__new__`, avoid real devices and processes while executing actual reference methods. Linux constants, fake one-tick jobs and capture-only writes are disclosed in the generators. Not actual epoll, RF, device startup, USB permissions or router acceptance. |
| Runtime/config/routing/state/blackhole/placeholder generators | A synthetic owner, interface and clock, a captured packet sink or constructor, or a source-extracted actual parser/planner isolates decisions. Executing reference code this way is not real startup, restart or network behavior. Placeholder constructor capture does not prove Python daemon initialization. |
| Git page/template/repository/work fixtures | Static-template and executable `.allowed` classification overrides on Windows, frozen generation time and stats, synthetic node/job context and explicit Git Unicode settings; see the generator disclosures. A default-rendering oracle, not every installed optional backend or unmodified Windows executable-file semantics. |
| Rnodeconf command/planner/signing generators | Captured serial, tools, filesystem and sleeps, and the original AST-extracted flasher planner; ephemeral independent RSA public verification. No private signing key is retained as a hardware identity. Not a real flasher, download or EEPROM device. |
| `Interop\live_rnsh_node.py` and POSIX peer | Real POSIX reference sessions and protocol; the client driver bypasses the interactive upstream UI. True EOF requires an exact child-produced acknowledgement. A clean return and a positively observed missing-callback race are distinguished, never patched into success. A cancellation without an observed exited child, a RUNNING listener and an absent return code fails. Windows native uses ConPTY, not a fake Python POSIX backend. |
| Actual I2P topology | Explicit opt-in public network and authenticated router provisioning. i2pd `[sam] singlethread=false` is nondefault, not an RNS patch. Java local-destination `i2cp.disableLoopback=false` permits same-router local delivery and passes restarted DATA. Forced-public `true` still fails restart for .NET and upstream, and local passes are not public-tunnel acceptance. There is no zero-hop or hidden reference-side lease/readiness shim. |
| Real lxmd | The nondefault accepted transfer limit is raised for large resources. Delivery-endpoint acceptance is separate from reverse origination and propagation synchronization. |

Fixtures may use public deterministic test keys for reproducibility; these are not publisher identities. A simulator's agreement with our framing is not a second independent Python node. Reference-side source remains clean, but that fact alone does not negate the explicitly disclosed in-process adapters.

## Known gaps

The active list of missing and partially implemented capabilities is maintained in [TODO.md](../TODO.md). The contract tables give each contract's current status and evidence; the active list does not replace those classifications.

In summary:

- Desktop RNode BLE is partial Windows software, without physical acceptance or Linux/macOS providers.

These statements do not change the narrower implemented software and live-peer coverage recorded in the tables.

### Intentional differences

The following are intentional differences or bounded implementations:

- explicit start/dispose and cancellation;
- the Core codec separated from routing;
- static, AOT-safe factories and message values instead of Python dynamic imports and reflection;
- strict crypto and diagnosed malformed input;
- bounded queues, peers, resources, requests and observer overload;
- no optional observer required for core processing;
- explicit authorization for remote execution, editors, templates, discovery, firmware and trust;
- native branding and documented CLI streams and statuses;
- no Python REPL;
- native atomic state and spool formats, with owner-only Unix creation and operator-owned Windows ACLs;
- asynchronous .NET stream semantics and native process ownership.

Bounds are observable compatibility differences, not proof of unlimited upstream acceptance. Mandatory cancellation and resource cleanup are joined, but arbitrary noncooperating user code or drivers cannot be forcibly made safe. The ratchet cache-hit context fix, strict token padding and key validation, ConfigObj syntax and default restrictions, the fixed failure-isolation policy, hard-link-backed atomic create-only publication, pinned rnsh EOF/exit quirks, and parser-specific output/exit differences all stay documented, including where valid flows pass.

## Source integrity, signatures and publisher trust

The .NET `rngit` client has retrieved missing Git objects from the hosted source over Reticulum, with a disclosed seed, a nonzero received bundle, recorded refs, commit and tree IDs, and strict Git object checks. Git object consistency does not authenticate the endpoint, the locator or the publisher. A checksum, a transport connection, a signed announce, an embedded key or a self-contained release signature alone does not establish publisher identity.

The published maintainer release identity is `bc7291552be7a58f361522990465165c`. A trusted-release claim requires an independently obtained and validated binding to that identity, and verification of the relevant manifest, artifact, commit or tag, including tampering, wrong-signer, missing signature/key and author/tagger-mismatch cases. `rngcs check-novalidate` is structural only. Git allowed-signers is not the pinned signer's trust database, and choosing `--signer` is caller policy, not authenticated key discovery. This document does not claim publisher authentication.
