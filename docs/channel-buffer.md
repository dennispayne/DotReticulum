## Protocol behaviour

A Channel envelope has a six-byte big-endian header; its declared length is tolerated even when it differs from the remaining payload length. The two-byte stream header carries the EOF flag, compression flag and 14-bit stream ID. Messages are delivered once and in order across sequence wrap, with a 48-message receive window. The sending window adapts to delivery and RTT; retries preserve the sequence and envelope, and link shutdown disconnects outstanding receipts.

A channel stream uses compressed chunks when applicable, drains buffered data before normal EOF, and bounds decoded chunks to 16 KiB. The reader has a configurable unread-byte limit (default 1 MiB); overflow fails the reader and aborts its link rather than silently dropping already-proven data. Writes wait on the channel's receipt/window signal with cancellation. Reads complete on data, EOF, cancellation, disposal or link closure.

### Proofs and the bounded reorder window

Pinned `Channel.py:353-395,398-440` checks a 48-message receive lookahead but
admits sends based on outstanding proof count. `Link.py:1147-1155` proves Channel
packets before receive-window validation. Later packet proofs can therefore let
a sender pass an earlier lost sequence far enough to have data discarded yet
acknowledged. The original native implementation reproduced this with the real
Python receiver: exactly 802,816 bytes received, next sequence 49 and no EOF.
Restricting only our sender fixed outbound delivery but left the reverse
large-stream failure with the unchanged upstream sender.

The native sender now also caps sequence distance from the oldest unproved
envelope at `WindowMax`. The native receiver proves retained/delivered frames and
duplicates, but not rejected ahead-of-window or malformed frames; those can be
retried after the gap closes. Proof creation remains protected by the live
link's ownership lock. Wire formats, receive capacity and retry timers are
unchanged. This is an intentional native reliability hardening, not a claim that
the pinned implementation has the same behavior; no reference-side shim is used.
Focused tests cover both boundaries across sequence wrap and duplicate reproving;
the actual native/Python constrained flow proves complete delivery in both directions.

`RawChannelReader` uses one lazily allocated circular byte buffer. Its default
unread-byte capacity is 1 MiB; callers may select `maxBufferedBytes` on the
constructor or factory. Reads do not copy/reallocate the remaining buffer.
Capacity exhaustion raises `IOException`, releases storage and closes the whole
link. The protocol has no application-consumption credit message; Channel
proofs acknowledge retained/delivered data, not application consumption.
Blocking an ingress thread or dropping an already proven chunk cannot provide
honest reader backpressure.
Write backpressure instead awaits the channel's real receipt/window signal,
with cancellation, rather than polling.

Library-owned stream readers run separately from optional message observers.
Channel ordering and stream buffering continue even if an optional observer
blocks. Optional messages have a 256-message queue and one worker; queue
exhaustion closes the link. The reorder ring holds at most 48 ahead-of-gap
messages. Each channel permits 64 optional handlers and 64 stream readers.
Each reader permits 64 ready callbacks and has one worker with one coalesced
notification, not a new task/thread per packet. Callback exceptions are logged
with stream context. Disposal discards queued callback notifications.
Internal stream readers take precedence over public observers: unlike upstream's
single registration-ordered callback list, an optional observer cannot consume
or delay the stream protocol. Public observer registration order and first-true
short-circuiting are preserved for messages not claimed by a stream reader.
Message constructors and `Pack`/`Unpack` remain synchronous codec contracts and
must not perform blocking application work.

`Channel.HandlerCompletion` and `RawChannelReader.ReadyCallbacksCompletion`
expose current owned work. An already executing synchronous application callback
cannot be forcibly canceled; it must return itself. Shutdown/disposal releases
protocol waiters and pending work without waiting for such a callback. Applications
must keep callbacks short and must not block on their own completion task.

Unlike Python's nonblocking `RawIOBase.readinto()` returning `None`, .NET reads
wait until data, EOF, cancellation, disposal, or link closure. Closure drains
already buffered bytes before returning EOF; disposal throws
`ObjectDisposedException` and clears storage. A sender's EOF is terminal.
Zero-length reads return zero without consuming data. Canceling a pending read
does not retain an orphaned `WhenAny` wait on channel closure.
Factories return these native .NET streams (or a reader/writer tuple), not
Python's `BufferedReader`/`BufferedWriter`/`BufferedRWPair` wrappers. `WriteAsync`
consumes the supplied memory or reports failure; `WriteChunk` supplies the
upstream-style nonblocking, partial-write operation. There is no extra hidden
write buffer requiring a flush.

Writes on one writer are serialized with close. A write already accepted by the
writer finishes before EOF; new writes after close starts fail as disposed.
Concurrent close calls share one operation; a canceled/failed close may be retried
without sending a duplicate successful EOF. Close has a monotonic 15-second
cancellation deadline and reports timeout instead of silently omitting EOF.
Normal link shutdown ends close without attempting a post-close EOF.
The fixed native deadline differs from upstream's `link.rtt * len(tx_ring)`
estimate (or 15-second exception fallback); EOF completion/idempotence and
cancellation are explicit native stream contracts rather than Python close quirks.

Pinned upstream accepts a declared envelope length that differs from the actual
remaining payload; this tolerance is retained and independently executed in the
fixture. The maximum outgoing message remains 65535 bytes even on larger-MDU
links. Stream chunks remain at most 16384 decoded bytes. Negative stream IDs are
rejected rather than being masked into a valid ID (an intentional .NET validation
difference).
The .NET outlet also reports a pending/closed link as not ready, rather than
upstream's explicitly unfinished always-true `is_usable` outlet predicate.
An outgoing envelope-length overflow raises the typed `TooBig` channel error
instead of Python's incidental `struct.error`.

## Interoperability and lifecycle

Actual pinned Python nodes exercise direct upgraded-MTU Channel traffic in both endpoint roles and a Python transport plus .NET transport path with 40-ms bridge RTT, selective Channel loss in both directions, Buffer streams, multipart resources, exhaustion teardown and fresh-link recovery. Live TCP bottlenecks cover 1,024 and 16,384 bytes, not every MTU or bearer. Sequence-wrap and RTT-boundary sweeps are vector evidence, not live-under-loss claims; slow-reader overflow, callback races and close/write/disposal failure paths are covered by focused tests rather than a live combined-failure topology or prolonged soak.

Core receive and receipt settlement continue independently of optional observers. Library stream handlers process protocol data; arbitrary user callbacks use bounded background work, log failures with stream context, and cannot disable unrelated protocol processing. Disposal stops queued notifications but cannot forcibly interrupt an already-running synchronous callback. `HandlerCompletion` and `ReadyCallbacksCompletion` expose owned callback work without making shutdown wait indefinitely for untrusted code.

## Retry encryption

The pinned `Packet.resend` repacks the unchanged plaintext Channel envelope. Link encryption therefore produces a fresh IV, ciphertext and packet hash for each retry, and each attempt has a fresh receipt. A proof for the current hash settles the current receipt; a proof for an expired hash does not. `Parity5ChannelRetryCryptoTests.ActualReferencePacketResendChangesCiphertextAndHashButPreservesEnvelopeAndSequence` validates the reference capture, and the .NET link retry test checks the corresponding receipt and proof behavior. The reference capture uses a synthetic established link and captures outbound packets; it does not claim a handshake or live-node exchange.
