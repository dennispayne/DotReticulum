# rnsh

`rnsh` is Reticulum's Channel-based remote shell utility. It ships in the pinned RNS repository (`RNS/Utilities/rnsh`) and is documented in the RNS manual. That version is included under the Reticulum License and is based on the original `rnsh` by Aaron Heise ([acehoss/rnsh](https://github.com/acehoss/rnsh), MIT License, Copyright (c) 2023 Aaron Heise), as its source headers state. It supports a persistent interactive terminal session and binary stdin, stdout, and stderr. It is distinct from `rnx -x`, which sends repeated request/response commands and does not provide a PTY. The wire protocol follows RNS 1.5.7 `RNS/Utilities/rnsh/protocol.py`, protocol version 1.

```sh
rnsh --config <shell-state> --rnsconfig <reticulum-config> -l -a <identity-hash> -b 0 -- /bin/sh
rnsh --rnsconfig <reticulum-config> -m <destination-hash> -- command argument
```

`--config` selects shell identity and authorization state (default `~/.config/rnsh` when present, otherwise `~/.rnsh`); `--rnsconfig` selects the Reticulum configuration. The listener identity defaults to `identity.default` or a sanitized service suffix; the initiator identity defaults to `identity`. The allowed identity file is `<shell-state>/allowed_identities`. `-l` starts a listener, `-s` selects a service identity suffix, `-i` selects an identity file, and `-p` prints identity (and listener destination) without starting the listener. `-b 0` announces once; an omitted `-b` does not announce. `-a` may be repeated to allow identity hashes. `-n/--no-auth` accepts any identity and is dangerous. `-N/--no-id` suppresses client identification. `-m/--mirror` returns the remote process status. `-w/--timeout` sets the positive finite connect/session deadline (default 30 seconds). `-v`/`-q` increase or decrease logging verbosity. `-A` appends remote arguments to the configured default command; `-C` rejects remote arguments. Arguments after `--` remain discrete argv values. Run `rnsh --help` for the full synopsis.

## Authorization and behavior

Starting a listener explicitly authorizes child process execution. Access is denied unless the initiator identity is in `-a` or the shell state's `allowed_identities`; that file is re-read for each new session. `-n` bypasses identity authorization. The default listener command is the platform shell (`cmd.exe` on Windows, otherwise `$SHELL` or `/bin/sh`); operator-supplied arguments are not concatenated into a shell command. `TERM` and `RNS_REMOTE_IDENTITY` are passed to the child. Use an allow-list and a constrained default command when shell access is not intended.

Protocol stream IDs 0, 1, and 2 carry stdin, stdout, and stderr. EOF flags delimit input; window messages carry rows, columns, and pixel dimensions. Output is read incrementally, channel queues are bounded, and the listener accepts at most 16 concurrent sessions. Child ownership and cancellation are explicit. Windows children use a kill-on-close Job; Linux and macOS PTY children use a new session/process group. Platform process-tree termination remains best effort for descendants that detach or escape OS ownership.

The native Windows terminal backend uses ConPTY; the native Linux and macOS terminal backends use `posix_spawn`, a PTY, process groups, and window ioctls. The initiator saves and restores terminal state, enters raw mode, polls window dimensions and rate-limits subsequent updates using the reference's `RTT * 25` interval, and supports `~~`, `~.`, `~L`, and `~?` escapes. The first changed size is compared against the command's actual initial dimensions, including changes during the handshake. Redirected pipe input bypasses escape processing to preserve arbitrary bytes. Windows ConPTY merges endpoints attached to its terminal surface; independently redirected endpoints remain lossless, and explicit inherited handles support mixed modes. POSIX termios behavior is not reproduced by ConPTY. All eight stdin/stdout/stderr pipe-versus-terminal combinations are exercised on Windows and Linux, including stream separation or terminal merging.

## Platform notes and differences from upstream

Native terminal backends are implemented for Windows, Linux and macOS. Actual macOS ARM64 execution has verified controlling-terminal resize, literal argv, interrupt delivery, process-group teardown, mode restoration with the documented PENDIN allowance, all endpoint combinations, delayed first read, the published-native terminal initiator and both pinned Python roles. Windows builds do not verify the Darwin native ABI. Redirected pipe processes are available on Windows and Unix. The pinned Python shell depends on POSIX-only `fcntl`, `pty`, `termios`, and `fork`, so its process/session implementation cannot run unmodified in Windows Python; Python live sessions use a Linux peer, including WSL when applicable.

Darwin uses its own `POSIX_SPAWN_SETSID`, open flags, window ioctls and 72-byte LP64 termios layout, including the arm64 variadic `ioctl` calling convention. XNU rejects extended master ioctls until the PTY replica has opened, so the parent first opens an owned, non-controlling replica. Retaining that replica alone was insufficient: XNU drains the controlling terminal before reporting a session leader's exit, so waiting for exit before starting reads can deadlock. An owned reader now drains terminal output immediately into a bounded 16-chunk queue, with backpressure when full. When only stdin uses the terminal, the unused primary output is drained without reporting it as stdout or stderr. The terminal reader releases the retained replica only when its input is idle and the child has exited; disposal cancels and joins the pump and releases the owned replica. Hosted run 40926579478 verified this correction on macOS; initialization and read errors remain fatal. Unlike Linux, Darwin applies spawn file actions before creating the new session. A fixed `/bin/sh` bootstrap therefore reopens one terminal endpoint after session creation to acquire the controlling terminal and foreground process group, then replaces itself using `exec -- "$@"`. The command remains discrete argv, never interpolated shell code; the shell adds no persistent helper process. All-pipe Darwin children use the same owned Unix spawn/wait backend as Linux. Its returned status is the reference's raw `waitpid` status masked with `0xff`, not a normalized shell exit code; a normal `exit 7` consequently reports zero. Windows retains native exit codes. The previous all-pipe Darwin fallback returned seven and failed the actual mixed-peer check. The ABI and ordering references are Apple's [XNU headers](https://github.com/apple-oss-distributions/xnu/tree/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/sys), [`tty_dev.c`](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/tty_dev.c#L989-L996), [`kern_exit.c:2286-2336`](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/kern_exit.c#L2286-L2336), [`kern_exec.c`](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/kern_exec.c), [`vfs_syscalls.c`](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/vfs/vfs_syscalls.c), and [Apple's arm64 ABI documentation](https://developer.apple.com/documentation/xcode/writing-arm64-code-for-apple-platforms).

The pinned server accepts `tcflags` but does not apply them; the native server likewise does not apply them to its child. In pinned POSIX upstream, `CallbackSubprocess.start.poll` masks `waitpid` status with `0xff`, causing ordinary POSIX nonzero exits to appear as zero. Windows uses native process exit codes. The native CLI's help and native terminal behavior are not claims of Python UI parity.

The pinned upstream has an EOF race: `close_stdin()` schedules termination while a waiter thread can reap the child before the regular polling callback observes termination, leaving the listener return code unset. The race is not guaranteed on every execution or platform. The live EOF probe waits for actual child readiness before closing stdin and requires exact child-produced acknowledgement of a zero-byte read. A clean completion must return zero; a bounded cancellation is accepted only with that acknowledgement and a fresh, link-correlated upstream observation that the child has exited while its listener remains RUNNING without a return code. An unexplained timeout fails. A successful session that keeps stdin open until the child exits must not be interpreted as proof that EOF completion works. DotReticulum owns child-input shutdown and teardown without reproducing the permanently hung listener; this is a behavior difference from the pinned implementation.

## Verification

XNU can add the transient `PENDIN` input-processing state when canonical input is
restored using `TCSADRAIN`. The terminal probe permits only that documented added
state bit, reports its actual before/after values if observed, and still compares
every other flag, speed, control byte and raw-mode transition exactly. It does
not flush input or change production restoration behavior. See
[`tty.c:1358-1391`](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/tty.c#L1358-L1391)
and [`termios.h:259`](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/sys/termios.h#L259).
Hosted run 40918584672 passed the revised probe. The prior failed probe did not
retain its byte-level diagnostic, so its exact cause is not retrospectively established.

`tests/DotReticulum.Applications.Tests/RnshTests.cs`, `RnshNativeTests.cs`, and `RnshLiveTests.cs` cover protocol, process ownership, terminal behavior, and live Python sessions. Windows and Linux x64 native endpoint combinations and Python interoperability are exercised, including binary streams, resize, loss/retry, cancellation, and recovery. Published NativeAOT terminal-hosted flows are exercised on both systems. `RnshDarwinTests.cs` adds actual-macOS controlling-terminal resize, literal argv, interrupt delivery, process-group teardown and delayed first-read cases; these explicitly skip elsewhere. Existing terminal-mode restoration, endpoint-combination and published-native terminal-flow cases are also enabled for macOS. Hosted run 40926579478, exact source f568802, passed all 29 rnsh cases on macOS, including the formerly failing delayed-first-read and stdin-only terminal cases, the first changed window size, both actual pinned Python roles and native terminal initiation. The overall run failed unrelated fixture assertions and the earlier cold-window resource scenario; it is not a passing overall CI result. The Python live driver exercises protocol sessions rather than upstream interactive UI. An observed EOF race remains a bounded negative reference result, not successful EOF completion.
