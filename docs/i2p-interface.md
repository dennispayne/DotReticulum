Observable criteria established before implementation:

* SAM 3.1 HELLO on every control/data socket; Ed25519 destination generation
  (`SIGNATURE_TYPE=7`), STREAM sessions, naming lookup for `.i2p` addresses,
  non-silent STREAM CONNECT/ACCEPT. Session control sockets stay owned/open.
  A destination line preceding incoming stream bytes is consumed without
  losing coalesced or fragmented packet bytes (`aiosam.py`, `tunnel.py`).
* Independent initiating and accepted child identities, not parent broadcast;
  parent sends do nothing. A failed peer cannot terminate other peers.
  Initiating streams reconnect (15 seconds, unlimited by default); accepted
  streams do not reconnect (`I2PInterfacePeer`).
* HDLC escaping, raw-frame HW MTU 1064, estimated bitrate 256000, IFAC
  default 16 bytes, full mode; connectable defaults false. Empty flag pairs
  are keepalive, not packets. Keepalive idle threshold 10 seconds,
  stale threshold 20 seconds, read timeout 110 seconds.
* Connectable private destinations persist as I2P base64 text in
  `storagepath/i2p/<hash>.i2p`. Prefer legacy
  `SHA256(SHA256(UTF8(name)))`; otherwise
  `SHA256(SHA256(UTF8(name)) || SHA256(transport_identity_hash))`.
  Restart reuses that destination; the public destination ends after
  certificate length at offsets 385..386 (`I2PController.server_tunnel`,
  `sam.Destination`). Private data must not appear in diagnostics/fixtures.
* Setup failures, malformed/oversized SAM lines, partial IO, cancellation,
  disposal during setup/accept/send, session loss, reconnect limits,
  bounded receive backpressure, restart and peer isolation have controlled
  simulator tests. Simulator evidence is **not actual I2P interoperability**.

## Integration and intentional .NET differences

`I2pPacketInterface(I2pPacketInterfaceOptions)` is an
`ISpawningPacketInterface`. Subscribe to `ChildConnected` before `StartAsync`;
children are already started and have their own receive stream, send path and
diagnostics. `I2pPacketPeer.IsInitiator` distinguishes configured outbound
peers from accepted streams. Initiating children implement
`IReconnectingPacketInterface` with stable object identity and connection
events. `Peers` is a bounded snapshot, not a second ownership transfer.
Dispose the parent to cancel/join all sessions, accepts, children and timers.
Start returns promptly while optional SAM/router setup retries in owned
background tasks; errors are available through `Diagnostic` and
`GetDiagnostics()["last_error"]`. Subscriber exceptions are isolated/reported.
The parent does not carry packet traffic itself.

Required runtime wiring (outside these new bearer files):

* Map `name`, `storagepath`, `connectable` (default false), and `peers`.
  Inject the actual transport identity's **16-byte hash**, not its public key,
  before starting a connectable bearer. Do not persist a placeholder hash.
* Apply upstream default full mode, bitrate estimate 256000, IFAC size
  **16 bytes**, IFAC network name/key and inherited routing/announce/ingress/
  egress policy to children through the existing manager. This bearer does not
  derive or apply IFAC a second time. Its raw 1064-byte bound includes IFAC
  overhead; ensure negotiated payload sizes leave that space.
* Pass generic `bitrate` as nullable `ConfiguredBitrate`: values below
  Reticulum's minimum **5** are ignored. The parent and accepted peers use
  the effective override in `Bitrate` and diagnostics. Hardware MTU stays
  1064 (`AUTOCONFIGURE_MTU=False`). **Initiating peers retain 256000**:
  upstream constructs/registers them in the I2P constructor before generic
  `interface_post_init` changes the parent. Accepted peers subsequently copy
  the parent's bitrate. Select these cases with `I2pPacketPeer.IsInitiator`,
  not by testing merely whether a child implements the reconnecting interface.
* Synthesize/restore Reticulum transport tunnels for **initiating** HDLC
  children on connect/reconnect; accepted children must not independently
  originate a tunnel solely because they expose connection diagnostics.
  I2P SAM sessions are distinct from authenticated Reticulum transport tunnels.
* Preserve per-child ingress identity: never broadcast to all children or
  reflect a packet back to its source. Parent counters aggregate only accepted
  children, matching upstream's `parent_count=False` for initiators.

`I2pPacketPeer` exposes `IPacketInterfaceChildPolicy`: initiators return
`InheritParentOutgoing=false`, `Outgoing=true`, `CountParentTraffic=false`;
accepted children return `true`, `true`, `true`. The manager can therefore
preserve initiating children's independent outgoing permission and exclude
their recursive packet/violation accounting without special-casing bearer
types. The focused `ChildPolicyExposesSourceOutgoingAndParentAccountingExceptions`
theory checks both policies without opening sockets.

Upstream I2P-specific runtime keys are `type=I2PInterface`, the section `name`,
`peers` (list; absent means none), and `connectable` (boolean; absent false).
`Reticulum.py` injects `storagepath`, `ifac_netname`, `ifac_netkey` and
`ifac_size` before construction. Generic user `ifac_size` is **bits** and is
converted to bytes; the I2P class default is **16 bytes / 128 bits**, not
16 bits. User IFAC names/key aliases remain generic runtime responsibilities.
The pinned constructor does not consume `listen_ip`, `listen_port`, `port`,
`target_host`, `sam_host`, `sam_port` or reconnect-limit keys. Explicit native
SAM endpoints, bounded peer limits and timer options are .NET API/testing
extensions, not invented upstream configuration keys.

Accepted children inherit parent mode/gravity/rate/control/IFAC policies.
Initiating children start full-mode, IN/OUT true and their own default control
and rate state; they copy IFAC settings at construction but do not copy the
post-initialized parent mode/bitrate. This ordering also means an omitted
IFAC size is still `None` on Python initiators before parent post-init fills
the 16-byte default. The native manager should consistently use the documented
16-byte default rather than reproduce that nullable-size failure edge; record
this safety normalization rather than claiming the Python constructor bug is
byte-tested behavior. Generic parent `outgoing=false` does not disable the
Python initiating children already registered IN/OUT true.

`SamHost=null` honors `I2P_SAM_ADDRESS`, default `127.0.0.1:7656`; explicit
host/port permit controlled testing without changing the environment. The
native bearer uses SAM data sockets directly rather than allocating extra
loopback proxy listeners: this preserves network bytes while avoiding the
vendored Python tunnel threads and their documented indefinite-shutdown bugs.
It generates destination keys through SAM, not a native reimplementation of
I2P cryptography. Session loss closes the affected streams and recreates owned
sessions. A ready initiating SAM session and its control monitor span ordinary
responsive remote stream EOF, naming/connect failures, setup timeouts
and reconnect delays. These retire only the attempted/active data socket.
Control-socket closure/failure or explicit SAM `INVALID_ID` retires the session;
an unsuccessful SESSION CREATE also closes its incomplete control socket.
Disposal or exhaustion of the configured retry limit closes all owned sockets.
Recreation reuses the same in-memory generated private destination. Even the
earlier per-stream-session implementation used that explicit private key, not
`DESTINATION=TRANSIENT`: its defect was loss of ready session/tunnel lifetime,
not regeneration of the private identity on every retry. Closing an interface
does not stop the router.

Exact pinned ownership trace:

* `tunnel.I2PTunnel._pre_run` generates the destination once and stores the
  `create_session` control writer on the tunnel; `I2PTunnel.stop` closes it.
* `ClientTunnel.run` calls `_pre_run` once, then its local `handle_client`
  starts a new `aiosam.stream_connect` for each accepted local TCP connection.
  `proxy_data` closes its stream writers on EOF; it does not close the
  tunnel's session writer.
* `I2PInterfacePeer.connect/reconnect` recreates local TCP sockets to that
  existing tunnel listener. Normal stream EOF does not set tunnel
  `status["exception"]` or `status["setup_failed"]`, so the controller's
  five-second status polling does not stop/recreate its SAM session.
* A reported SAM connection/setup error does set those tunnel status fields;
  `I2PController.client_tunnel` then calls `stop_tunnel` and returns false.
  Native retention of a still-valid session after a remote refusal/timeout is
  an intentional bounded recovery difference: only actual session/control
  failures rebuild the session, rather than discarding tunnel readiness for a
  peer-specific error.

The native setup timeout is a **shared** budget for destination generation,
session creation, naming and STREAM CONNECT, not a fresh budget for each
command. Production defaults to 30 seconds; actual-stream tests explicitly use
90 seconds inside their unchanged four-minute total deadline. Pinned
`aiosam.stream_connect`/`create_session` wait for SAM replies without an
application timeout. `ClientTunnel` keeps its session through a pending connect;
`I2PController.client_tunnel` stops/rebuilds the tunnel after a reported setup
failure. Native expiry cancels/closes the pending stream attempt but retains
an already-ready session for the next bounded attempt. Initial session
creation still has its setup deadline. The control monitor runs throughout
naming, pending STREAM CONNECT, packet exchange and reconnect delay: a dead
control socket cancels/joins the in-flight operation before recreating a
session. These bounded waits are not proof that a reported router failure was
caused by a native deadline.

Peer diagnostics expose `setup_phase`, `phase_elapsed_ms`, `setup_timeout_ms`,
`session_attempts`, `stream_connect_attempts`, `last_failure_phase` and
`last_error`, retaining sanitized SAM result codes but no private destination.
`session_id` and `local_i2p_b32` expose the non-secret session handle/public
identity so session reuse can be distinguished from stable child-object reuse.
The actual-router tests print these plus queued-child counts at child waits
and failure. In the native restart case, the wait for the **replacement**
accepted child occurs only after both initial-direction packet assertions,
server disposal, persisted-address/hash assertions and replacement session
readiness. A timeout there must not be described as failure of the initial
stream or as absence of all native packet delivery. Neither that partial
progress nor same-router traffic proves separately hosted remote-overlay
interoperability.

`StreamRetriesRetainSamSessionIdAndPublicIdentity` separately covers ordinary
EOF, a remote SAM rejection and a pending-connect timeout using the controlled
simulator, then verifies a second simulated data socket uses the **same** session
ID and public identity and carries a framed packet. Control loss during a
pending connect and explicit `INVALID_ID` have separate recreation tests;
watchdog reconnect retains the ready session and stable child, like ordinary
stream EOF. These assertions are
software lifecycle evidence, not actual I2P network acceptance.

### Interpreting an actual-router restart timeout

The i2pd 2.59.0 sources
([SAM.cpp](https://github.com/PurpleI2P/i2pd/blob/2.59.0/libi2pd_client/SAM.cpp),
[Streaming.cpp](https://github.com/PurpleI2P/i2pd/blob/2.59.0/libi2pd/Streaming.cpp))
do not support a first-application-payload accept deadlock:
`SAMSocket::Connect` calls `Stream::Send` even with zero buffered bytes;
`AsyncSend` schedules `SendBuffer`, which constructs the first SYN while the
stream status is new even without queued application data.
`StreamingDestination::HandleNextPacket` invokes the acceptor on the valid
initial SYN, and `SAMSocket::HandleI2PAccept` writes the remote identity line
without waiting for application payload. Conversely, STREAM STATUS OK is
issued after scheduling this connection, not after remote handshake success.
It is not evidence that the replacement server accepted the stream.

The native replacement server starts a new `AcceptLoopAsync` using its newly
created SAM session ID. After STREAM ACCEPT status, it waits for the peer
identity line before publishing a child. No missing re-arm is established by
`status=true` plus zero children alone. Upstream and native watchdogs send
repeated HDLC flag pairs after the ten-second packet-write idle threshold;
these deliberately do not increase packet traffic counters. Unchanged
`rxb`/`txb` therefore cannot establish absence of keepalive writes. The
110-second last-read deadline can explain a long disconnect delay without
proving a restart defect or successful recovery.

A failed replacement-child/packet assertion remains failed actual-router
restart/recovery acceptance, separately from passing initial exchanges,
Python exchanges or SAM persistence. Neither the managed suite nor a SAM OK
reply converts that gap into a hardware-only blocker.

#### Observed i2pd 2.59.0 destination-cleanup hazard

The retained failed run exposes a router lifecycle hazard, not evidence of a
Windows firewall failure. It does not establish the sole cause of the remaining
restart timeout. The router logged
`Clients: Local destination <server address> exists` at 18:35:56, when the
replacement reused the persisted key, then `SAM: I2P acceptor has been reset`
at 18:36:01. The five-second interval matches this source trace exactly:

* [`SAMBridge::CloseSession`, `SAM.cpp:1571-1622`](https://github.com/PurpleI2P/i2pd/blob/2.59.0/libi2pd_client/SAM.cpp#L1571-L1622)
  removes the session, stops its destination/streams, and, **only when
  single-threaded**, retains the old session for a five-second cleanup timer.
* [`ClientContext::CreateNewLocalDestination`, `ClientContext.cpp:407-422`](https://github.com/PurpleI2P/i2pd/blob/2.59.0/libi2pd_client/ClientContext.cpp#L407-L422)
  finds the destination under the same identity hash, restarts it, and returns
  that existing object to the replacement session.
* [`SAMSingleSession::~SAMSingleSession`, `SAM.cpp:1374-1377`](https://github.com/PurpleI2P/i2pd/blob/2.59.0/libi2pd_client/SAM.cpp#L1374-L1377)
  unconditionally calls `DeleteLocalDestination` when the delayed old session
  is destroyed.
* [`ClientContext::DeleteLocalDestination`, `ClientContext.cpp:377-389`](https://github.com/PurpleI2P/i2pd/blob/2.59.0/libi2pd_client/ClientContext.cpp#L377-L389)
  erases/stops the destination by hash without checking the replacement
  session's acquisition. Its new acceptor is reset; the new SAM control socket
  can still be open. Retaining the initiating session cannot repair a server
  destination deleted inside the router.

The inspected tag files have SHA-256:
`SAM.cpp=2ad9a2f98bcc86008e80569c6da19c1428215d9759e2140beda87fc2a9522e5a`,
`ClientContext.cpp=a46a871fbfe395b512c71db3f70ae5901f8cc32867511832151c4d17dd8ac0a1`.
These are router-source hashes, not changes to the pinned RNS provenance.
Garlic authentication/resend warnings also occur in that run, but are not
needed to establish the destination ownership error or independently
attributed to it.

The owned topology therefore explicitly uses the supported i2pd setting
`[sam] singlethread=false`. This avoids the deferred-destruction path; it is
not a source patch, tunnel/lease-set injection, simulator replacement,
application retry change or longer timeout. The setting is non-default:
[`Config.cpp:204`](https://github.com/PurpleI2P/i2pd/blob/2.59.0/libi2pd/Config.cpp#L204)
defaults it to true. Pass `-SingleThreadedSam` to reproduce that router-default
configuration. The runner prints the selected mode. An eventual passing run
with this workaround establishes only that configuration, **not recovery with
i2pd 2.59.0's default single-threaded SAM**. Native clients do not silently
change an operator's router settings or introduce a guessed cleanup sleep.

The subsequent actual run with `singlethread=false` **also failed** native
restart acceptance. It did not report destination reuse or a second delayed
acceptor reset; excluding that hazard did not resolve recovery.
Initial bidirectional packets passed at 02:15:58Z; replacement
SAM readiness followed at 02:16:16Z. The old initiating stream exhausted ten
router retransmissions at 02:17:32Z; its retry used the same SAM destination
and again received no handshake packets before the unchanged four-minute
deadline.

Another investigated recovery boundary was the initiating router destination's
cached remote state:
[`SAM.cpp:569-584`](https://github.com/PurpleI2P/i2pd/blob/2.59.0/libi2pd_client/SAM.cpp#L569-L584)
uses that destination's `FindLeaseSet` for each STREAM CONNECT.
[`Destination.cpp:190-231`](https://github.com/PurpleI2P/i2pd/blob/2.59.0/libi2pd/Destination.cpp#L190-L231)
returns its cached lease set until expiry (refreshing only near expiration).
[`Streaming.cpp:1866` onward](https://github.com/PurpleI2P/i2pd/blob/2.59.0/libi2pd/Streaming.cpp#L1866)
likewise requests replacement remote leases only when missing/expired;
stream retransmission failure does not flush that destination cache.
SAM naming success alone therefore does not refresh the already-ready
initiating destination's remote leases/garlic routing sessions.

A temporary native experiment recreated the ready SAM session after an
unresponsive stream terminated, preserving the private destination and child.
The seeded actual-router run exercised it and still failed replacement
acceptance. It was removed rather than landing an unproven behavior change:
stream staleness/EOF alone still does not discard a healthy control session.
Historical run diagnostics mentioning `stale_session_refreshes` describe
that experiment, not the committed API. No timer or delivery assertion was
weakened. The source trace does not establish a sole cause of recovery failure.

Safety/API differences: 64 incoming and 64 configured outgoing peers by
default, bounded 256-packet receive queues per child, bounded SAM lines
(16384 bytes), setup deadlines (30 seconds), serialized writes with no internal
unbounded transmit queue, cancellation-aware waits, strict malformed HDLC
discard rather than upstream's truncated/invalid-escape acceptance. The
shared decoder requires at least three frame bytes; real Reticulum packets
already exceed this. NetworkStream owns completion of partial underlying
socket writes. A cancelled/failed packet write retires that stream so a
partially written frame cannot corrupt the next packet. Idle flags do not
increment packet counters; like upstream they repeat on each watchdog tick
after ten seconds without a packet write.

Key files use create-new staging in the destination directory followed by
non-overwriting rename, preventing interrupted writes and overwriting a
concurrently created identity. Existing corrupt/oversized files are reported,
not silently regenerated. New Unix files are owner-read/write only. **Windows
operators must protect the storage directory using appropriate ACLs.** Private
destination strings necessarily enter managed text APIs for SAM and upstream
file compatibility; decoded byte and read buffers are cleared, but immutable
strings cannot be reliably zeroed. Private keys/reply text are excluded from
diagnostics, and the committed vector contains only a synthetic **public**
destination.

Malformed accepted-peer SAM tokens, base64 encodings and public-destination
structures are remote input failures: the bearer reports `InvalidDataException`
with a sanitized contextual message and retains the original validation error
as `InnerException`. The public `PublicBase32` helper still uses
`ArgumentException` for invalid caller arguments. Rejected remote metadata does
not expose a child or stop unrelated streams/the accepting session.

## Opt-in actual-router acceptance

### Why a fresh isolated router is not a default stream topology

Inspection of i2pd tag `2.59.0` establishes:

* [`SAM.cpp`](https://github.com/PurpleI2P/i2pd/blob/2.59.0/libi2pd_client/SAM.cpp)
  `ProcessSessionCreate`/`HandleSessionReadinessCheckTimer` withhold
  SESSION STATUS OK until the destination's `IsReady()`.
* [`Destination.h`](https://github.com/PurpleI2P/i2pd/blob/2.59.0/libi2pd/Destination.h)
  `IsReady()` requires a non-expired lease set **and** outbound tunnels.
  [`Destination.cpp`](https://github.com/PurpleI2P/i2pd/blob/2.59.0/libi2pd/Destination.cpp)
  `RequestLeaseSet` requires a known floodfill. SAM's STREAM CONNECT and
  NAMING LOOKUP use that discovery path; merely hosting both sessions in
  one fresh router does not bypass it.
* [`TunnelPool.cpp`](https://github.com/PurpleI2P/i2pd/blob/2.59.0/libi2pd/TunnelPool.cpp)
  supports zero-hop tunnels. SAM supports I2CP `inbound.length` and
  `outbound.length` options. However, zero-hop readiness alone does **not**
  provide the missing floodfill/lease-set discovery. The pinned RNS I2P
  configuration does not expose these session options. Injecting them would
  be a disclosed test/native extension, not unmodified source configuration;
  this slice deliberately does not do so or substitute cached lease sets.
* [`NetDb.cpp`](https://github.com/PurpleI2P/i2pd/blob/2.59.0/libi2pd/NetDb.cpp)
  also triggers reseeding for insufficient floodfills, so setting
  `reseed.threshold=0` alone does **not** disable external bootstrap.
  [`Reseed.cpp`](https://github.com/PurpleI2P/i2pd/blob/2.59.0/libi2pd/Reseed.cpp)
  respects disabled IPv4/IPv6 and empty HTTPS/Yggdrasil URL lists.

Consequently the default owned, network-isolated process executes the narrower
real-SAM persistence case. Running default-source STREAM acceptance requires
actual usable tunnels/lease-set discovery; the runner requires the operator's
explicit `-AllowPublicNetwork -RunStreamTests`. Even if those cases pass,
**same-router endpoints are not separately hosted router/remote-overlay
interoperability**, and PLAIN packets do not establish IFAC or authenticated
Reticulum transport-tunnel/resource acceptance.

### Owned topology runner and exact commands

`tests\Interop\invoke-i2p-topology.ps1` accepts an already obtained i2pd binary
and creates only a unique repository-local `TestResults` directory. It refuses
an occupied SAM port. The process is non-service/non-daemon, with an owned
datadir/config, empty owned tunnel files and loopback SAM 3.1.
SAM threading is explicitly **per-destination** (`singlethread=false`) to
avoid the diagnosed i2pd 2.59.0 cleanup race; `-SingleThreadedSam` restores
the router-default mode for reproduction. This is a disclosed router setting,
not a change to upstream RNS or the native bearer's protocol.
Default isolation binds IPv4 NTCP2 explicitly to the SAM endpoint's loopback address
on a separate owned port; it disables IPv6/SSU2, transit, reseed URLs, address-book
subscriptions, NTP/peer clock sync, UPnP, Yggdrasil and unrelated
HTTP/proxy/BOB/I2CP/control listeners. No existing router configuration is
read or changed. The core settings are supported by
[`Config.cpp`](https://github.com/PurpleI2P/i2pd/blob/2.59.0/libi2pd/Config.cpp);
this is process isolation, not a fabricated RNS bearer protocol.

i2pd 2.59's
[`Daemon_Singleton::start`](https://github.com/PurpleI2P/i2pd/blob/2.59.0/daemon/Daemon.cpp)
returns failure before starting client services/SAM if both
`IsBoundNTCP2()` and `IsBoundSSU2()` are false. In
[`Transports.h`](https://github.com/PurpleI2P/i2pd/blob/2.59.0/libi2pd/Transports.h)
these names test **service-object existence**, not actual listener sockets.
The runner nevertheless creates and checks a real loopback-only listener,
rather than merely satisfying that pointer check. Its isolated settings are:

```ini
ipv4 = true
ipv6 = false
address4 = 127.0.0.1
host = 127.0.0.1
reservedrange = false
netid = 222
[ntcp2]
enabled = true
published = true
port = <separate owned port>
proxy =
[ssu2]
enabled = false
```

`ntcp2.published=false` is **not** a listening configuration:
[`NTCP2Server::Start`](https://github.com/PurpleI2P/i2pd/blob/2.59.0/libi2pd/NTCP2.cpp)
creates acceptors only for published RouterInfo addresses. Here "published"
means the address in the **owned private router's** RouterInfo is the explicit
loopback address, not permission to bind a wildcard/public address.
`address4` controls both the acceptor's local address and outgoing NTCP2 socket
binding. `reservedrange=false` is required because `RouterInfo::ReadStream`
otherwise rejects loopback addresses; the daemon applies that override before
initializing RouterContext. The non-main `netid=222`, empty seed sources,
fresh datadir, disabled subscriptions/time sync and loopback binding prevent
this topology from joining the public overlay. No ready tunnels or packet
delivery are manufactured. `TransportPort=0` selects an available owned
loopback port, or the caller can specify one explicitly. The runner checks that
both SAM and this real NTCP2 listener respond; coordinator execution must also
record the OS listener addresses. This is not an OS namespace/firewall boundary.

Public-network mode uses main net ID 2 and normal transport binding only with
explicit authorization. It requires `-CertificatesDirectory` pointing to the
extracted package's public certificate root (containing reseed/family
certificates), passes that with `--certsdir`, and explicitly enables reseed
signature verification. It never disables verification to hide missing
certificate files. Certificate warnings on an isolated empty datadir are not
evidence of public bootstrap or streaming.

For an explicitly seeded public bootstrap, `-SeedRouterInfoDirectory` may
point to a previously owned router's **netDb directory only**. It requires
`-AllowPublicNetwork`, resolves/validates the source before launch, and copies
only bounded regular `routerInfo-<I2P-hash>.dat` files from their standard
`r<first-hash-character>` directories into the new owned NetDb. Symlink/reparse
sources and unexpected layouts are rejected. No whole datadir is reused:
router keys, private SAM destinations, profiles and lease sets are not copied.
The unmodified router remains responsible for validating signed RouterInfos;
the filename allowlist is not signature verification. Normal reseed signature
verification remains enabled. The runner prints source-directory provenance
and copied-file count. This is non-default **public NetDb bootstrap**, not
cached destination leases, fabricated tunnels or an RNS/native protocol change.
It does not guarantee the advertised peers remain reachable.

### Separate pinned-Python restart diagnostic

`-ReferenceRestartOnly` selects exactly one case in
`Parity6I2pReferenceRecoveryTests`, **not** the normal four-case live group.
It requires explicit `-AllowPublicNetwork`, PythonExecutable and UpstreamPath;
it cannot be combined with `-RunStreamTests`. Public RouterInfo seeding and
the disclosed SAM threading selection remain available. Replace
`-RunStreamTests` with `-ReferenceRestartOnly` in the command above.

The case uses two separate verified, unmodified pinned Python RNS processes,
not a native bearer or Python protocol reimplementation. It asserts actual
PLAIN callbacks both directions, terminates only its owned server process,
then starts a new process using the same owned configuration directory.
The initiating Python process survives unchanged. It verifies the persisted
private-key file by SHA-256 without logging its contents, stable public b32/
application destinations, replacement accepted peer, and callbacks both
directions after restart. All setup, pre-restart traffic and recovery share
the same unchanged **four-minute deadline**.

The thin adapter's explicit `--resume-directory` validates that the existing
configuration matches rather than overwriting it; `--reverse-aspects` swaps
only the two application's incoming/outgoing aspect labels so the Python
peers can address each other. Packet construction, callbacks, SAM sessions,
framing and reconnect remain the actual upstream methods. Process termination
is deliberate: pinned `I2PController.stop` iterates its tunnel dictionary keys,
so `detach()` alone is not proof that the original SAM sessions disappeared.
No reference-side tunnel, readiness or cleanup shim is injected.

This diagnostic compares reference recovery under the same router settings;
neither success nor failure is native restart acceptance. The seeded native
run already exercised session refresh (two sessions, one refresh, unchanged
public identity) and still failed replacement acceptance despite passing
initial native bidirectional traffic and both mixed Python roles. The
reference restart result is recorded separately below.

Its first execution exchanged both initial callbacks but correctly failed the
replacement b32 assertion: the original non-transport config used upstream's
ephemeral transport identity. `Transport.py:320-334` already writes/loads
`storage/transport_identity`, then replaces the active identity with a fresh
ephemeral one unless transport is enabled or `static_transport_identity` is
true. Graceful persistence alone cannot preserve that ephemeral active hash.
The I2P filename includes the active hash, so a new process selected a new
private destination despite the old key file still existing.

The restart diagnostic now explicitly sets upstream's supported
`static_transport_identity = Yes` on the server and replacement only
(`Reticulum.py:513-515`), without enabling routing or writing identity bytes
itself. This non-default fixture configuration is reported in adapter
observations. Before/after assertions compare active public transport hash,
persisted transport identity file SHA-256, I2P filename/key SHA-256, exactly
one I2P key file, and b32 before interpreting stream recovery. The ordinary
four-case live group retains its original config. The corrected diagnostic
ran against the explicitly seeded, per-destination-threaded i2pd 2.59.0:
initial callbacks in both directions and every persistence assertion passed,
but no replacement accepted peer arrived before the unchanged four-minute
deadline (**0 passed, 1 failed**). The surviving initiator reported broken

not native acceptance or proof of a sole router cause. The earlier
identity-changing run is not a same-destination restart counterexample.

The restored-source diagnostic subsequently failed the same accepted-peer
